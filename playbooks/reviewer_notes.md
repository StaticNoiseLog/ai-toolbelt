**Most important points when instructing the reviewer LLM**

1. **Give it a clear, critical role**  
   Explicitly tell it to act as a senior/principal engineer (or security specialist, performance specialist, etc.) whose
   job is to find real problems, not to be encouraging. Instruct it to be strict and to prefer false positives over
   missed issues.

2. **Supply the original requirements / acceptance criteria**  
   The reviewer must know what the code was *supposed* to do. Without the task description, user stories, or API
   contract, it can only do generic style/correctness checks and will miss intent mismatches.

3. **State the language, framework, version, and style rules**  
   Include the exact stack, coding standards, linting rules, and any project-specific conventions. Also mention known
   constraints (performance targets, memory limits, no external network calls, etc.).

4. **Tell it the code was generated by another LLM**  
   Ask it to pay special attention to common LLM failure modes: hallucinated APIs or methods, incomplete error handling,
   missing edge cases, overly optimistic assumptions, duplicated logic, weak typing, and “looks correct but is subtly
   wrong” patterns.

5. **Define the review axes and severity levels**  
   Explicitly list what matters most (correctness, security, robustness, performance, readability/maintainability,
   testability, adherence to the given requirements). Require every finding to have a severity (Critical / High /
   Medium / Low) and a short justification.

6. **Demand structured, actionable output**  
   Ask for:
    - Location (function/file + approximate lines or a short code snippet)
    - Problem description
    - Why it matters
    - Concrete suggested fix or alternative
    - Confidence level

7. **Provide tests (or the lack of them) as context**  
   If unit/integration tests exist, include them. If they don’t, instruct the reviewer to flag missing coverage for
   important paths.

8. **Limit scope and forbid unnecessary praise**  
   Tell it to focus only on the supplied code and the given criteria. Instruct it not to rewrite the entire solution
   unless asked, and not to pad the response with compliments.

**Recommended granularity**

The sweet spot is **a coherent implementation task or a self-contained chunk that has clear requirements (and ideally
tests)**.

| Granularity                   | When it works well                                 | Main drawbacks                                         | Recommendation                                     |
|-------------------------------|----------------------------------------------------|--------------------------------------------------------|----------------------------------------------------|
| Single function/method        | Pure logic, algorithms, small utilities            | Loses surrounding context and data-flow issues         | Good for targeted checks                           |
| Chunk covered by tests        | Feature slice with unit/integration tests          | Excellent signal (tests + requirements)                | **Strongly preferred**                             |
| Specified implementation task | One ticket/story with clear acceptance criteria    | Best balance of context and focus                      | **Best overall**                                   |
| Entire application            | Final architecture / security / consistency review | Context-window limits, diluted attention, noisy output | Use only for high-level pass after smaller reviews |

**Practical workflow that works best**

- Break the work into small, well-specified tasks.
- Have the generator LLM implement one task at a time.
- Immediately feed that task’s code + original requirements + tests (if any) to the reviewer LLM.
- Fix the critical/high issues, then move on.
- Do a broader review only after several related tasks are stable.

Reviewing at the level of a single well-defined task (or a tested chunk) gives the reviewer enough context to catch real
bugs and design problems without overwhelming it or diluting its attention. Entire-application reviews are useful later
for cross-cutting concerns (architecture, consistency, security posture), but they should not be the primary or first
review step.
